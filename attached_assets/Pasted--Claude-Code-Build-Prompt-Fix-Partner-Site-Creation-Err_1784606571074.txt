## Part 1 — Fix the "unexpected JSON response" error on partner site creation

### 1.1 What this error actually means

"Unexpected [token in] JSON response" from the client almost always means the frontend called `response.json()` on a response that wasn't actually JSON — usually because the server-side route threw an unhandled exception and the platform (Vercel) returned its own HTML error page instead of a JSON error body, or the route crashed before it ever sent a response, or the request hit the wrong route entirely (e.g. a 404 HTML page). This is a symptom, not the root cause — don't just wrap the fetch in a try/catch and swallow it; find why the server-side call is failing.

### 1.2 Reproduce and diagnose, in this order

1. Trigger the partner-creation flow from the admin panel exactly as Zayne does, and capture the **actual raw response** (not just the parsed error) — log the response status code, `content-type` header, and raw body text before attempting to parse it as JSON, both in a local/dev reproduction and by checking Vercel's function logs for the live deployment.
2. Check Vercel's function logs for the partner-creation API route around the time of a failed attempt — look for an unhandled exception, a timeout, or a cold-start/env-var issue.
3. Walk through everything that route does and check each for a likely failure point:
   - **RLS policy on `partners`**: confirm the authenticated admin's session actually has insert permission on `partners` per the RLS policy built in the earlier god-mode/partners work — a blocked insert from Postgres/Supabase can throw an error that, if uncaught, produces exactly this symptom.
   - **Unique constraint violations**: `partners.slug` and `partners.custom_domain` are both unique — if the admin submitted a slug that already exists, Postgres will reject the insert with an error; confirm this is caught and returned as a clean JSON `{ error: "This URL is already taken" }` (or similar), not left to bubble up as an unhandled exception.
   - **Foreign key issues**: if `distributor_id` is included in the payload but references a distributor that doesn't exist (or is null when the column expects a valid reference in some code path), confirm this is validated before the insert, not left to fail at the database level uncaught.
   - **Vercel domain API call**: if the creation flow also attempts to add a custom domain in the same request (from the earlier custom-domain work), and that external API call fails, times out, or the required Vercel API token is missing/misconfigured, confirm this failure is caught and doesn't crash the entire request — partner creation and custom domain attachment should probably be handled as separable steps so a domain API failure doesn't block the partner record from being created at all.
   - **Response serialization**: confirm every code path in the route — success and every error case — explicitly returns `NextResponse.json(...)` (or equivalent) with an appropriate status code; there should be no code path that can return undefined, throw past a try/catch, or return HTML.
4. Once the actual root cause is identified, fix it there — not just at the response-formatting layer.

### 1.3 Required fix pattern (apply regardless of root cause found)

- Wrap the entire route handler in a top-level try/catch that guarantees a JSON response on every possible exit path, including truly unexpected errors — log the real error server-side, but always return something like `{ error: "..." }` with a proper status code to the client, never let a raw exception produce an HTML platform error page.
- Return specific, actionable error messages for the known failure cases above (duplicate slug, invalid distributor, domain API failure) rather than a generic "something went wrong" — the admin needs to know what to fix.
- On the frontend, don't call `.json()` blindly — check `response.ok` and `content-type` first, and show the admin a clear error message (from the JSON body if present, a generic fallback if the response truly wasn't JSON at all) rather than an unhandled parse exception in the console.

### 1.4 Surface the created site's link

Once creation succeeds, the admin UI must immediately show (and let the admin copy) the new partner site's live URL — both the default slug-based URL and, if a custom domain was requested and is still pending, a clear status indicator ("Live at songtai-partners.vercel.app/p/slug — custom domain pending verification") rather than leaving the admin to go find the link elsewhere. This should already be straightforward once creation actually succeeds and returns the created `partners` row (including `slug`) as part of its JSON response — make sure the response includes it.

## Part 2 — Partner site hero redesign: bigger image, inspired by heynesh.com

### 2.1 What to take from the reference site

`heynesh.com` (a Webflow developer's portfolio) uses a hero pattern worth adapting — not copying wholesale, since it's a very different kind of business, but the *structural* ideas apply well to a partner storefront:

- A **large, prominent photo** sits directly in the hero, not a small thumbnail off to the side — the image is a primary visual anchor, roughly comparable in visual weight to the headline text, not a decorative afterthought.
- **Small floating badge/stat elements** overlaid near the image (in their case: client-logo badges and a "80+ Projects" stat chip) — for Songtai partner sites, the equivalent should be certification badges (ISO/GMP/Halal — already part of the site's trust content) or a short trust stat, placed as small floating elements near the hero image rather than buried lower on the page.
- **Bold, short headline typography** paired with a brief supporting line and one clear CTA button — avoid a wall of hero copy.
- Generous whitespace around the hero rather than a cramped, multi-element hero competing for attention.

### 2.2 Apply this to the partner site hero specifically

- Increase the hero image size significantly from its current treatment — the partner's `hero_image_url` (or the main site's default hero image as fallback, per the earlier partners build) should be large enough to be the visual focal point of the homepage on both desktop and mobile, not a small banner strip.
- Use `next/image` with `priority` (this is above-the-fold, should not be lazy-loaded) and correct `sizes` for a genuinely large hero image without hurting load performance — this must stay consistent with the CDN/image-optimization work already done sitewide, not regress it just to make the image bigger.
- Add 1–2 small floating trust badges (a certification badge, or a short stat like years of heritage/certifications count already used elsewhere on the site) positioned near the hero image, echoing the reference site's badge treatment — keep these using the existing gold token reserved for certifications (from the theme build), don't introduce new colors for this.
- Keep the hero headline/subtitle using `hero_title_en/fr`/`hero_subtitle_en/fr` from the partner's row (with the documented fallback to main-site defaults if unset) — layout changes here, not the underlying content model.
- Confirm the redesigned hero still meets the WCAG AA contrast requirements from the theme build for any text overlaid on or near the image (add a subtle scrim/gradient behind text if needed, using the theme's existing gradient/token approach rather than an arbitrary new overlay color).
- Mobile: confirm the larger image doesn't push the CTA and headline below the fold on common phone screen sizes — test at a few common breakpoints, not just desktop.

### 2.3 Non-negotiables
- This applies to the partner site template only (`partners-platform`) — do not change the main `songtai-life` site's hero as part of this work unless explicitly asked.
- No regression in Lighthouse/Core Web Vitals from the earlier CDN/performance work — a bigger hero image must still be properly optimized (`next/image`, correct format/sizing), not just a larger unoptimized file.
