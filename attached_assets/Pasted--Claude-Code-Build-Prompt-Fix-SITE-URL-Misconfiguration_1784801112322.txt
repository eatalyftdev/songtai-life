## 1. Root cause, found directly in the code — this is not a partner-resolution bug

`server.ts` line 520:
```ts
const SITE_URL = (process.env.SITE_URL ?? "https://songtailife.cm").replace(/\/$/, "");
```
and `.env.example`:
```
SITE_URL="https://songtailife.cm"
VITE_SITE_URL="https://songtailife.cm"
```

**`songtailife.cm` is a custom domain that is not yet configured/live.** Every generated partner/referral link in the system — including the "shared platform URL" shown to the admin right after creating a partner (`server.ts` ~line 1854: `` `${SITE_URL}/p/${slug}` ``), WhatsApp notification messages, and sitemap URLs — is built from this value. If the deployment's real, reachable address is actually `something.vercel.app` or `something.netlify.app` (because the real custom domain isn't live yet), then **every link the system generates is pointing at a domain that doesn't resolve**, which is exactly what produces the symptom "the main site can't load, it's trying to load a partner site" — the browser isn't failing to load the actual app; it's failing to load a broken link that was generated with the wrong base URL. `PartnerContext.tsx` and `App.tsx`'s routing were checked directly and do not contain any logic that would block the plain `/` route from loading — this is an environment configuration issue, not an application bug.

## 2. The fix

1. **Determine the actual live URL(s)** the app is currently reachable at — check the Vercel project dashboard and/or Netlify site dashboard for the real assigned domain (e.g. `songtai-life-main.vercel.app`, or whatever Netlify assigned).
2. **Set `SITE_URL` and `VITE_SITE_URL` to that real, currently-reachable URL** in the environment variables of whichever platform(s) are actually serving traffic right now — not the aspirational `songtailife.cm` domain until that domain is actually purchased, pointed at the deployment, and verified live.
3. If **both** Vercel and Netlify are live simultaneously (per the platform-agnostic deployment work) with two different default domains, each platform's own environment variables should hold **its own** correct `SITE_URL`/`VITE_SITE_URL` — don't set the same single value in both if their actual reachable domains differ. Every partner link generated must resolve correctly regardless of which deployment served the admin's request.
4. Once a real custom domain (e.g. `songtailife.cm`) is actually purchased and fully verified/live in DNS, `SITE_URL`/`VITE_SITE_URL` can be updated to that domain across all environments — at that point it becomes the correct canonical value. Until then, it must reflect wherever the app is genuinely reachable today.
5. **Remove the hardcoded fallback risk**: change the fallback in `server.ts` from defaulting to a specific domain name to either (a) failing loudly at startup with a clear log message if `SITE_URL` isn't set in production, so a missing env var is caught immediately rather than silently generating broken links, or (b) falling back to something guaranteed reachable in that environment (e.g. derived from the request's own host header for locally-generated links) — pick whichever is more appropriate for this codebase's deployment practices, but do not leave a silent fallback to an unverified domain in place.
