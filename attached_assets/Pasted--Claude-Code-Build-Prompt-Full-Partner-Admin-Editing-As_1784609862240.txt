## 2. Part A — Full admin editing of every partner site

Every field on a `partners` row that can be set at creation must also be editable afterward, from the admin panel, at any time — this was implied but not made explicit in the earlier build, make it explicit now:

- Slug (with the same uniqueness/URL-safety validation as creation — changing a live partner's slug should warn the admin clearly that their old URL will stop working, since anyone using it will get the "not available" state; consider whether to support a redirect-from-old-slug grace period, and if you do, keep it simple — a redirect table isn't required unless it's trivial to add without expanding scope)
- WhatsApp number, contact email
- Hero title/subtitle EN & FR, hero image
- Status (pending/active/suspended)
- Linked distributor (assign, reassign, or unlink)
- Custom domain (see Part B below — this is the more involved piece)

Use the same edit form the creation flow uses, pre-filled with the current values, submitting to an update endpoint that follows the exact same "always return real JSON, never let an exception produce an HTML error page" pattern established in the previous fix — apply that standard to every admin-facing partner API route, not just the one that was broken.

Every field change takes effect on the live partner site immediately (it's read from Supabase at request time, same as the rest of the site) — no redeploy required for any of this.

## 3. Part B — Custom domain is optional at creation, added/changed anytime, and takes real DNS time

This is the core behavior change requested: **a partner site must be fully creatable and usable with no custom domain at all.** The slug-based URL (`songtai-partners.vercel.app/p/[slug]` or subdomain equivalent) is the default, always-available address. A custom domain is an optional upgrade added whenever the partner/admin is ready — never a blocker to creating or using the site.

### 3.1 Creating a partner with no custom domain yet
- `custom_domain` stays null, `domain_status` stays `'none'`
- The partner site is fully live and functional at its slug URL from the moment of creation
- The admin UI should show something like "No custom domain yet — live at `[slug URL]`. Add a custom domain anytime." — not an error, not a required field, not a blocking step

### 3.2 Adding a custom domain later (from the edit screen)
1. Admin enters the domain they want to attach.
2. Backend calls the Vercel API to add the domain to the `songtai-life-partners` project, gets back the required DNS records (CNAME, and/or TXT for verification — use whatever Vercel's API actually returns, don't assume a fixed record shape).
3. Set `domain_status = 'pending_verification'`, `vercel_domain_added_at = now()`, `domain_check_attempts = 0`, store any verification token Vercel provides.
4. Show the admin the exact DNS record(s) to add at their registrar — record type, name/host, and value, copyable — with a plain-language note that **DNS changes are not instant**: propagation commonly takes anywhere from a few minutes to 24–48 hours depending on the registrar and the domain's TTL settings, and that's normal and expected, not a failure.
5. **The slug URL keeps working exactly as before, unaffected, for the entire time the custom domain is pending.** The partner is never taken offline or left without a working link while DNS propagates.

### 3.3 Background verification (don't make the admin babysit it)
- Build a scheduled job (Vercel Cron or equivalent, running on a reasonable interval — e.g. every 15–30 minutes) that finds every partner with `domain_status = 'pending_verification'`, re-queries Vercel's domain verification status for each, and:
  - On success: set `domain_status = 'verified'`, update `domain_last_checked_at` — the domain is now live automatically, no further admin action needed, and (per the request) **both the slug URL and the custom domain remain active and reachable** — do not redirect the slug URL away once a custom domain verifies, unless a future requirement explicitly asks for a canonical redirect; for now, both addresses should just work.
  - On continued failure: increment `domain_check_attempts`, update `domain_last_checked_at`, leave `domain_status` as `pending_verification` — do not mark it `failed` just because one check didn't pass; DNS propagation is genuinely slow sometimes. Only move to `failed` after a sensible extended threshold (e.g. no success after 7 days / a high attempt count) so a real misconfiguration eventually surfaces instead of polling forever silently — surface this as a flag in the admin overview list, not a scary error, since the fix is usually just "check the DNS record was entered correctly."
- Also give the admin a manual "Check now" button on the partner's edit screen for the impatient/verify-it-worked case, calling the same check logic on demand rather than waiting for the next scheduled run.

### 3.4 Changing an already-attached custom domain
- Admin can replace a `verified` (or still-`pending_verification`) custom domain with a different one from the edit screen.
- Backend must properly remove the old domain from the Vercel project (call the corresponding Vercel API) before or alongside adding the new one — don't leave orphaned domains attached to the Vercel project that no longer match any `partners` row.
- Reset `domain_status` to `'pending_verification'` for the new domain and repeat the flow in 3.2–3.3. The slug URL and the previous custom domain's traffic implications: once the old domain is removed from Vercel, requests to it will stop resolving to this site — that's expected; make sure the admin UI communicates this clearly when they initiate a domain change ("Your current domain will stop working once you save this change — make sure the new domain is ready").
- Also support simply **removing** a custom domain entirely (going back to slug-only), which should call Vercel to detach it and reset `domain_status` to `'none'`, `custom_domain` to null.

## 4. Non-negotiables
- A missing or pending custom domain is never an error state anywhere in the system — it's the normal default. Only a `failed` status (after the extended threshold in 3.3) should read as something needing attention.
- The slug-based URL must be permanently reliable — it's the fallback that guarantees a partner site is never fully offline, regardless of what's happening with their custom domain.
- Every domain-related Vercel API call (add, check status, remove) must be wrapped with the same "always return real JSON, log the real error server-side" pattern from the earlier fix — a Vercel API hiccup must never crash the admin panel or corrupt a partner's editable state.
- Confirm the Vercel API token used has both add and remove domain permissions on the `songtai-life-partners` project — removal is just as necessary as addition for the "change your domain" flow to work cleanly.
