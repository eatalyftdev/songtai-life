1. SUPABASE AUTH — MAKE IT RELIABLE
═══════════════════════════
- Single `supabase` client instance (lib/supabase.ts), never re-instantiated per component.
- Wrap the app in an `AuthProvider` (React Context) that:
  - Calls `supabase.auth.getSession()` once on mount, then subscribes via `supabase.auth.onAuthStateChange` for the life of the app — never re-fetch session on every render.
  - Loads the matching `profiles` row (role, locale) alongside the session and exposes `{ user, profile, role, loading }` from the context.
  - Exposes `loading` explicitly so protected routes can show a loading state instead of a flash of the wrong UI or a premature redirect before the session resolves.
- `ProtectedRoute` component: checks `loading` first (render nothing/spinner), then checks `user` + `role` against an allowed-roles prop, redirects only once state is settled — this directly avoids the redirect-loop class of bug from the Eatalyft/Firebase migration lessons already baked into this project.
- Session persistence: confirm `persistSession: true` and `autoRefreshToken: true` are set in the Supabase client config (default, but verify explicitly) so refresh doesn't silently log users out.

DEFAULT ADMIN ACCOUNT — seed script (`scripts/seed-admin.ts` or a one-off SQL block), NOT hardcoded credentials in the app:
```sql
-- Run once after auth.users row exists (create the user via Supabase Dashboard > Authentication,
-- or via supabase.auth.admin.createUser() in a server-side seed script using the service role key)
insert into profiles (id, email, role, locale, must_change_password)
values ('<the-created-auth-user-uuid>', 'admin@songtailife.cm', 'superadmin', 'en', true)
on conflict (id) do update set role = 'superadmin';
```
Add a `must_change_password boolean default false` column to `profiles` if not already present. On login, if `must_change_password = true`, redirect to a forced password-change screen before allowing access to any admin route — same pattern already used on Eatalyft's superadmin seeding.

Never commit the admin password anywhere. Generate it once, display it in the terminal/seed script output only, and require the change on first login.

═══════════════════════════
- Roles: `customer | distributor | content_editor | admin | superadmin` (already defined in `profiles.role`).
- Frontend: `ProtectedRoute` (above) takes an `allowedRoles` array; wrap every `/admin/*` and `/distributor/*` route.
- Backend (the real boundary — client-side checks are UX only): every table that needs role-gated writes already has `is_admin()`-based policies from the last migration. Extend this pattern for `content_editor`:
```sql
create or replace function is_content_editor_or_above()
returns boolean language sql security definer stable set search_path = public as $$
  select exists (
    select 1 from profiles
    where id = auth.uid() and role in ('content_editor','admin','superadmin')
  );
$$;

drop policy if exists "editor_blog_posts_write" on blog_posts;
create policy "editor_blog_posts_write" on blog_posts
  for all using (is_content_editor_or_above()) with check (is_content_editor_or_above());
```
- Also pin `set search_path = public` on the existing `is_admin()` function if not already done (security hardening flagged previously).
- Nav/menu items conditionally render based on `role` from `AuthProvider`, but this is purely cosmetic — the real enforcement is the RLS policies above.

3. RATE LIMITING
═══════════════════════════
Add a lightweight Postgres-backed rate limiter usable from both client actions and Edge Functions:
```sql
create table rate_limit_events (
  id uuid primary key default uuid_generate_v4(),
  bucket text not null,        -- e.g. 'login', 'contact_form', 'newsletter'
  identifier text not null,    -- IP or email
  created_at timestamptz default now()
);
create index on rate_limit_events (bucket, identifier, created_at);

create or replace function check_rate_limit(p_bucket text, p_identifier text, p_max_attempts int, p_window_seconds int)
returns boolean language plpgsql security definer as $$
declare v_count int;
begin
  select count(*) into v_count from rate_limit_events
  where bucket = p_bucket and identifier = p_identifier
    and created_at > now() - (p_window_seconds || ' seconds')::interval;
  if v_count >= p_max_attempts then
    return false;
  end if;
  insert into rate_limit_events (bucket, identifier) values (p_bucket, p_identifier);
  return true;
end;
$$;
```
Apply it:
- **Login**: before calling `supabase.auth.signInWithPassword`, call `check_rate_limit('login', email, 5, 300)` (5 attempts per 5 min) via RPC; block and show a cooldown message if it returns false.
- **Contact form / newsletter**: same pattern keyed by email or a client-derived identifier, 3 submissions per 10 minutes.
- **Withdrawal requests**: keyed by `distributor_id`, prevents spam-clicking the payout button.
- Enable RLS on `rate_limit_events` with `insert` allowed via the function only (`security definer`), no direct client read/write.
