Continuing the Songtai Life build on Supabase. Right now several admin forms likely accept a raw image URL text field (paste-a-link) instead of a real file upload — this pass audits every image/media input across the admin panel and converts it to an actual upload into Supabase Storage via the shared `<MediaUploader />` component, so every asset the site displays is one you actually host and control, not a link to someone else's server that can change, disappear, or get rate-limited without warning.

═══════════════════════════
1. WHY THIS MATTERS (context for the build, not just a preference)
═══════════════════════════
A URL-based image field means: the image can vanish if the external host takes it down, it can be swapped by whoever controls that URL (a real security/trust risk on a public-facing brand site), it's not covered by your own CDN/caching, and you have zero control over its dimensions/format/optimization. Every image on Songtai Life should live in Supabase Storage (`media`, `documents`, or `testimonials` buckets already established) so it's yours: backed up with the rest of your data, served consistently, and immune to a third party breaking your site.

═══════════════════════════
2. AUDIT — FIND EVERY URL-TEXT-INPUT FOR MEDIA
═══════════════════════════
Search the admin panel codebase for any form field currently labeled/typed as a URL string for an image, video, or document, rather than a file upload. Based on the schema built so far, this almost certainly includes:
- Products: `images[]` (if currently a comma-separated URL list or repeatable URL text inputs)
- Blog posts: featured image field
- Hero carousel / `hero_carousel` (or `gallery_images` reused for this) entries
- Gallery images: `url` column, if currently populated by pasting a link rather than uploading
- Testimonials: `video_url` (this one may legitimately stay a URL if pointing to an external host like YouTube — see Section 5 exception)
- Product categories: `image_url`
- Gallery albums: any cover image
- Site Settings → Branding: `logo_url`, `logo_dark_mode_url`, `favicon_url`
- Site Settings → SEO Defaults: `og_image_url`
- Media Center documents (catalogues/brochures) if currently linked rather than uploaded

Every one of these gets converted per Section 3 below.

═══════════════════════════
3. STANDARDIZE ON THE SHARED MediaUploader COMPONENT
═══════════════════════════
If `<MediaUploader />` already exists (speced in an earlier pass — drag-and-drop, progress bar, preview, file-type/size validation, uploads to a Storage bucket and returns the public URL), confirm it's the *only* image input mechanism used anywhere in the admin panel. If any form still has a plain `<input type="text" placeholder="Image URL">`, replace it with this component.

`<MediaUploader />` behavior to confirm/enforce:
- Accepts drag-and-drop or click-to-browse, restricted to actual image MIME types (`image/jpeg`, `image/png`, `image/webp`, `image/avif` — reject anything else client-side before it even attempts upload).
- Shows a live preview thumbnail immediately (from the local file, before upload completes) so the admin sees what they picked, then swaps to the real uploaded image once the Storage call resolves.
- Enforces a sane max file size (e.g., 5MB for product/blog images, 10MB for hero/carousel assets) with a clear error message, not a silent failure or a stuck progress bar.
- On successful upload, writes the returned Supabase Storage public URL into the parent form's state — the admin never sees or types a URL manually; it's populated automatically.
- Supports **replace** (upload a new file into the same field, old file optionally deleted from Storage or left orphaned with a cleanup job later — decide based on whether you want image history/rollback) as well as **remove** (clear the field entirely).
- For fields that need multiple images (Products, Gallery bulk upload), support multi-file selection/drag in one action, uploading each to Storage and appending to the array field, with per-file progress and the ability to reorder or remove individual images before saving.

═══════════════════════════
4. STORAGE PATH ORGANIZATION
═══════════════════════════
Structure uploads into clear subfolders within the `media` bucket so the library stays navigable as it grows, rather than dumping every file into one flat root:
media/
products/{product_id}/{filename}
blog/{post_id}/{filename}
gallery/{album_id or 'uncategorized'}/{filename}
hero-carousel/{filename}
categories/{category_id}/{filename}
branding/{filename}          -- logo, favicon, OG default image
documents/
media-center/{filename}      -- catalogues, brochures
Update `<MediaUploader />` to accept a `folder` prop so each usage (ProductForm, BlogForm, GalleryUpload, CategoryForm, BrandingSettings) passes its correct destination path — this keeps the Media Library grid (built in an earlier pass) meaningfully browsable/filterable rather than one giant undifferentiated list.

═══════════════════════════
5. THE ONE DELIBERATE EXCEPTION — EXTERNAL VIDEO
═══════════════════════════
`testimonials.video_url` (and any Events/Blog embedded video) is allowed to remain a URL field **only** when pointing to an external video host (YouTube/Vimeo) that's meant to be embedded via iframe, since re-hosting video files yourself in Supabase Storage has real bandwidth/storage cost and streaming-quality tradeoffs. Add a small validation/preview: paste a YouTube/Vimeo URL, the form shows an embedded preview player, and rejects clearly-invalid URLs (not a YouTube/Vimeo domain) with a clear message. If a distributor/admin wants to upload a raw video file instead of linking one, provide that as a genuine file-upload alternative (to the `testimonials` bucket) with a toggle between "Paste video link" and "Upload video file" — but the *image* thumbnail for that testimonial still goes through `MediaUploader`, never a pasted URL.

═══════════════════════════
6. MIGRATE EXISTING URL-BASED DATA
═══════════════════════════
If any products/blog posts/gallery images/categories already have externally-hosted URLs saved from before this fix, they'll keep displaying correctly (nothing breaks retroactively), but they're not yet "owned." Add a one-time admin utility:
- `/admin/media-library` gets a "Find externally-hosted images" scan button — checks existing image URL fields across products/blog_posts/gallery_images/product_categories for any URL that doesn't start with your Supabase Storage domain.
- For each flagged record, show a "Re-host this image" action: fetches the external image server-side (an Edge Function, to avoid CORS issues and keep the admin's browser out of it), uploads it into the appropriate Storage folder from Section 4, and updates the record's field to the new Supabase Storage URL — with a before/after preview so the admin can confirm before committing.
- This can be run one record at a time or as a batch "Re-host all flagged images" action with a progress list, given there may be several dozen from the earlier product-catalog work.

═══════════════════════════
7. DATABASE-LEVEL SAFEGUARD (optional but recommended)
═══════════════════════════
To prevent this regressing later (someone hand-editing a record via SQL, or a future form change accidentally reintroducing a raw text input), add a soft check constraint on the key image columns:
```sql
alter table products add constraint images_are_supabase_hosted
  check (
    images = '{}' or
    (select bool_and(img like 'https://%.supabase.co/storage/%') from unnest(images) as img)
  );
```
Apply the equivalent pattern to `blog_posts.featured_image_url`, `gallery_images.url`, `product_categories.image_url`, and the branding fields in `site_settings` — this makes it a hard database rule, not just a UI convention, that these specific fields can only ever contain your own Storage URLs. (Skip this constraint on `testimonials.video_url` given the deliberate YouTube/Vimeo exception in Section 5.)

DELIVERABLE: Every image input across the admin panel — Products, Blog, Gallery, Hero Carousel, Product Categories, Gallery Albums, Branding, SEO Defaults, Media Center documents — replaced with the shared `<MediaUploader />` component uploading directly to organized Supabase Storage folders, no admin ever pastes a raw image URL again, existing externally-hosted images can be re-hosted via a one-time migration utility, and (optionally) a database constraint enforces that these fields can only ever contain Supabase-hosted URLs going forward.
