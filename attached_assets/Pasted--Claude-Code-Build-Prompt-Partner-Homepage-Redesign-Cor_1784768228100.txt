## 1. Ground truth — the architecture you're already asking for mostly exists

This is a **single Vite + React 19 + React Router SPA**, backed by a single **Express server** (`server.ts`), deployable to both Vercel and Netlify (`netlify/functions/server.ts` wraps the same Express app via `serverless-http`) — there is no separate "partners platform" deployment. One deployment serves everything.

**Tenancy today** works via `PartnerContext.tsx`: it watches the URL path for `/p/:slug`, fetches that row from the `partners` table (Supabase), and injects it into context. `HomeSection.tsx` already reads `usePartner()` and overrides hero title/subtitle/image when a partner's fields are set (falling back to the main site's `homepage_sections` content otherwise). `PartnersPage.tsx` (admin) already has full CRUD, custom-domain fields, and status management. `server/domain-provider.ts` already implements the exact provider-agnostic pattern (Vercel implementation live, Netlify stubbed) from earlier planning.

**This means**: "one shared admin panel," "one shared database," and "an admin edit reflects on every partner instantly" are **already true today**, structurally — because it's the same app, same database, same React tree, just rendering different data per route. You are not building that from scratch. Confirm it stays true through this work (don't accidentally fork logic per-partner), and focus your actual effort on the three real gaps below.

## 2. Gap #1 (the important one) — custom domains don't actually resolve to a partner yet

`PartnerContext.tsx` only ever checks `location.pathname` for `/p/:slug`. If a partner's custom domain (e.g. `janedoe-wellness.com`) is attached via the existing domain-provider flow and a visitor hits `https://janedoe-wellness.com/`, the pathname is `/` — **`PartnerContext` will not recognize this as a partner site at all**, and the visitor will simply see the main company homepage, not `janedoe-wellness.com`'s partner content. The custom-domain lifecycle (add/verify/remove) is fully built server-side, but nothing currently maps a verified custom domain back to its partner once traffic actually arrives there.

**Fix**: extend tenant resolution to also match on hostname, not just path:
- On app boot (or in `PartnerContext`'s resolution logic), read `window.location.hostname`.
- If it matches the main site's own known domain(s) (the production domain(s) the main app is served from — pull this from an env var, don't hardcode it), behave exactly as today (path-based `/p/:slug` resolution, or no partner context at all).
- If it does **not** match the main site's domain, treat the hostname itself as a lookup key: query `partners` where `custom_domain = <hostname>` and `status = 'active'` and `domain_status = 'verified'`. If found, provide that partner's context for the entire session on this domain (effectively, the whole app renders as that partner's site rooted at `/`, not `/p/:slug` — routes within it should work the same way, just without the `/p/` prefix).
- If the hostname doesn't match any verified partner, show the same `PartnerNotAvailable` treatment already built (or a sensible "domain not configured" variant) rather than silently falling through to the main company site — a stray/misconfigured domain must never accidentally serve the main company's content.
- This check needs to work correctly both client-side (SPA route resolution) and should be sanity-checked against what the Express server does for the initial HTML response/SEO meta tags for that request too, since `server.ts` already does sitemap/URL generation work per-domain-context in places — confirm the initial server-rendered `<title>`/meta reflects the correct partner when a custom domain is hit directly, not just the client-side React state.

## 3. Gap #2 — hero image upload UX in the admin Partners form

`PartnersPage.tsx` currently has the hero image as a plain URL text input with a placeholder note: *"Hero image URL (upload to Media Library first)"* — meaning today, adding a partner's photo requires Zayne to separately open the Media Library, upload there, copy the resulting URL, then paste it into this form. Replace this with a direct upload control in the Partners form itself:
- A drag-and-drop / file-picker upload widget right in the hero image field, using the same Supabase Storage bucket and upload pattern already established for the Media Center/gallery admin sections — don't invent a second upload mechanism, reuse the existing one.
- On successful upload, auto-populate `heroImageUrl` with the resulting public/CDN URL — no manual copy-paste step required.
- Show a preview thumbnail of the currently-set hero image in the form, with a clear "replace" / "remove" action.
- Keep the raw URL input available as a fallback/advanced option (e.g. behind a toggle or secondary field) for cases where an admin wants to link an already-hosted image without re-uploading — but the primary, default interaction should be upload-and-go.

## 4. Gap #3 — homepage/hero redesign: more attractive, more animated, Songtai-branded (not the reference palette)

A "Corporate Trust" design system reference was provided as design-direction inspiration — it's built around an indigo/violet SaaS aesthetic with isometric 3D card transforms, gradient headline text, blurred gradient "blob" backgrounds, colored (not neutral-gray) shadows, and elevated cards that lift on hover. **Take the structural/motion ideas, not the color palette** — Songtai Life already has its own verified, WCAG-AA-checked token system in `src/index.css` (`--color-primary: #016934` Songtai Green, `--color-accent: #FF6B3D`/`#E7380D` Vermillion family, `--color-gold` for certifications, the Fraunces/Inter font pairing, and a full light/dark surface system) — every technique below must be re-skinned to those tokens. Do not introduce indigo, violet, or any color outside the existing system.

Apply these specific techniques (already-installed `motion` library, i.e. Framer Motion's successor, should be used for all of this — it's already a dependency):

- **Dimensional hero visual**: where `partner.hero_image_url` (or the main site's default hero visual) renders — currently a flat image in a `lg:col-span-6` panel — give it a subtle isometric treatment: a slight 3D tilt (`rotateX`/`rotateY` via `motion`'s `style` transforms, a few degrees only, not a gimmick), a soft **colored** shadow using `--color-primary`/`--color-accent` at low opacity (not a neutral gray shadow), and a gentle hover/idle micro-motion (a slow breathing scale or a subtle parallax tilt that responds to pointer position, kept tasteful and non-distracting). This is the single biggest visual upgrade requested — make the partner's own photo (or the default hero visual on the main site) feel like the dimensional focal point of the page, not a flat rectangle.
- **Gradient headline treatment**: for the hero headline, apply a `background-clip: text` gradient using Songtai Green → Vermillion (the same gradient direction/stops already established as the site's "signature ribbon" element from the theme work) on a portion of the headline for emphasis — not the whole headline, per the "split headline" technique (most of the text in the normal foreground color, a few emphasized words in the gradient).
- **Soft blob backgrounds**: add large, heavily-blurred, low-opacity radial gradient shapes in the hero and a few other key sections (About/Story, the opportunity-steps section), built from `--color-primary`/`--color-accent`/`--color-gold` at 10-20% opacity, positioned absolutely behind the content for atmospheric depth — purely decorative, must not interfere with text contrast (re-verify WCAG AA on any text that sits near/over a blob).
- **Elevated cards with colored shadows**: audit feature/benefit cards, product cards, and testimonial cards already in `HomeSection.tsx` — apply a resting soft shadow tinted with `--color-primary` (not neutral gray), with a stronger lift + shadow intensity increase on hover (`translateY` + shadow scale via `motion`), consistent with the "Elevated Card System" idea from the reference, but in Songtai's palette.
- **Micro-interactions**: arrow icons that translate on hover (CTA buttons, "read more" links), image scale-on-hover where product/gallery images appear, staggered entrance animations (`motion`'s `variants` + `staggerChildren`) for the feature grid and stats row as they scroll into view, respecting `prefers-reduced-motion` throughout (disable/simplify all of the above when set — check the existing `index.css`/component patterns for how reduced-motion is already handled elsewhere on the site and match that convention).
- **Certification/trust badges near the hero**: small floating badge chips (using `--color-gold`, reserved for exactly this per the existing token system) near the hero visual — reusing the certification content already on the site (ISO/GMP/Halal) rather than inventing new claims.

This redesign applies to `HomeSection.tsx` and `HeroCarousel.tsx`, which are shared by the main site and every partner instance — so improving them once improves every partner site automatically, consistent with the single-deployment model. Do not fork a separate "partner homepage" component; enhance the existing shared one, using the existing `usePartner()` override pattern for what's already partner-specific (title/subtitle/image), and add nothing here that isn't already data-driven from either `homepage_sections` or `partners`.

## 5. Non-negotiables
- No new color palette — every visual technique above must resolve through the existing `--color-*` tokens in `src/index.css`, verified in both light and dark mode.
- No regression to the shared-everything model: an edit in the main admin panel (hero carousel, homepage sections, partner fields) must continue to reflect instantly on both the main site and every partner instance, since they're the same deployment reading the same Supabase data — verify this explicitly after the redesign, don't just assume refactoring didn't break it.
- The custom-domain hostname-resolution fix in section 2 is a real functional gap, not a nice-to-have — a partner's custom domain is not actually usable end-to-end without it, regardless of how well the domain-attachment lifecycle (already built) works.
- Respect `prefers-reduced-motion` for every new animation added.
- No regression to Core Web Vitals — run Lighthouse before/after on the homepage.
