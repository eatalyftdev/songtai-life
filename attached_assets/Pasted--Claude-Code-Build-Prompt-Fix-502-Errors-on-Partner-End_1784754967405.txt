## 1. The actual error, read correctly

Live network log from the admin panel:

```
POST /api/admin/partner/create   502   1425ms
GET  /api/admin/partners         502   902ms
```

**A 502 is meaningfully different from the "unexpected JSON" symptom fixed earlier.** A 500 with a JSON error body means the app caught an error and responded properly. A **502 means the serverless function itself crashed, failed to boot, or the platform's edge/proxy layer couldn't get any valid response from it at all** — this happens *before* your try/catch logic even gets a chance to run, or the function never returned anything at all. Wrapping the route in more try/catch will not fix a 502 on its own if the function is crashing at a level try/catch can't reach (a build/bundling error, an unhandled exception during module initialization, a missing environment variable causing a crash on cold start, or an unrecoverable runtime error). Diagnose properly before patching.

**Notably, `GET /api/admin/partners` is a plain list/read endpoint failing too** — that's a strong signal this isn't really about the create flow's domain-attachment logic (which was the focus of the earlier fix); something more fundamental is broken for the `partners` table specifically, likely one of:
- A genuine schema mismatch between what the deployed code expects and what's actually in the live database
- A broken or misconfigured RLS policy on `partners` causing every query (including a simple `SELECT`) to error
- A missing/incorrect environment variable (Supabase URL/service key) affecting every server-side call touching this table
- A bundling/build error introduced by recent code changes that only manifests at runtime

## 2. Important context — check this first, it's the most likely root cause

**The `partners` table (and several others) have had multiple schema migrations applied directly against the live Supabase database** over the course of this project's recent work — `partners` gained `domain_status`, `domain_verification_token`, `vercel_domain_added_at`, `created_by_admin`, `pending_contact_name/phone`, `domain_last_checked_at`, and `domain_check_attempts` across several migrations, and `distributors`/`rank_tiers` were also altered. **Confirm these migrations exist in the codebase's own migration history** (e.g. a `supabase/migrations/` folder, if this project uses the Supabase CLI migration workflow) and that generated TypeScript types (`supabase gen types typescript ...` or equivalent) have been regenerated and committed since these changes. If the deployed application code was written or last built against an older shape of `partners` (fewer columns, different constraints), a mismatch between what the ORM/query builder expects and what the live schema actually has can absolutely cause exactly this kind of hard crash — check this before assuming the bug is in application logic.

**Action**: pull/diff the current live schema for `partners`, `distributors`, and `rank_tiers` against whatever the codebase currently assumes (types, query selects, insert payloads), reconcile any mismatch, and regenerate/commit types as part of this fix.

## 3. Diagnosis steps, in order

1. Check the platform's function logs (Vercel function logs, or equivalent) for the exact timestamps of both failed requests — get the real error/stack trace, not just the 502 status code. This is the single most useful piece of information and should be checked before writing any code.
2. Confirm the route handlers for `POST /api/admin/partner/create` and `GET /api/admin/partners` actually exist, build successfully, and don't throw at import/module-initialization time (a crash during import — e.g. a missing env var read at the top of the file, outside any function body — will crash the whole function before a single request is even handled, which matches a 502 much better than a normal in-request error would).
3. Confirm required environment variables (Supabase URL, service role key, any Vercel/domain API tokens introduced in the custom-domain work) are actually present and correctly set in the environment this was tested against — a missing var referenced without a guard is a classic cause of this exact failure mode.
4. Re-run the queries these routes perform directly against the database (outside the app, e.g. via the Supabase SQL editor) using the exact same select/insert shape the code uses, to confirm the schema itself supports it and no RLS policy silently blocks it for the role/session being used.
5. Only after identifying the actual cause, apply the fix — likely one or more of: correcting a stale column reference, regenerating types, fixing a missing env var, or fixing an RLS policy.

## 4. Required fix pattern (apply regardless of specific root cause found)

- Every route must handle its own errors and never crash at module load — any environment variable access, client initialization, etc. that could throw must be guarded, with a clear startup-time error logged server-side rather than a silent crash that only shows up as a 502 to the client.
- Once the actual crash is fixed, still apply the "always return real JSON, never let an exception bubble to a platform error page" pattern from the earlier fix, as defense in depth — but understand that pattern alone does not fix a true 502, it only improves the error experience for the cases it can actually catch.
- Add basic monitoring/alerting (or at minimum, clear structured server-side logging) on these two routes specifically, since they're core to partner onboarding — a silent repeat of this failure should be visible before Zayne has to notice it manually again.

## 5. Shared-domain-by-default, host-agnostic — finalize this behavior

This continues the platform-agnostic and custom-domain-lifecycle work already speced. Confirm/implement, regardless of which host is currently serving the app:

- **Every partner site works immediately on a shared platform domain** — `{slug}.songtai-partners.vercel.app` if hosted on Vercel, `{slug}.songtai-partners.netlify.app` if hosted on Netlify, or the equivalent pattern for any other host — selected via the `HOSTING_PROVIDER`/site-URL environment variables already established in the platform-agnostic work. This is the default, always-on address for every partner, with or without a custom domain.
- **No custom domain required, ever, for a partner site to function** — reconfirm this explicitly as part of this fix, since it's directly relevant to why creation shouldn't be blocked by anything domain-related.
- **Custom domain setup is a distinct, later, opt-in step with its own clear flow**, run from the partner's edit screen in admin:
  1. Admin/partner enters the desired domain.
  2. System calls the appropriate domain-provider adapter (per the provider-agnostic interface built in the platform-agnostic work) to register the domain against whichever host is currently serving the partner platform.
  3. System displays the exact DNS records required (type, host/name, value) for the admin to add at their domain registrar — real values returned by the provider's API, never generic placeholder instructions.
  4. Domain status sits in `pending_verification` until DNS is confirmed — during this entire time, the partner's shared-domain URL keeps working unaffected.
  5. Only once DNS is verified does the custom domain go live — and even then, the shared-domain URL keeps working alongside it (per the earlier requirement that both stay active).
- This entire custom-domain flow must work the same way regardless of host — if the current deployment target changes (Vercel ↔ Netlify ↔ elsewhere), only the underlying provider adapter implementation changes, not the admin-facing flow or the database model.
