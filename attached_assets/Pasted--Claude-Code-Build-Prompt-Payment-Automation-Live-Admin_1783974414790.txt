## 3. System 1 — Automated MeSomb payment verification

**Flow required:**
1. User selects an entry pack (Iron/Bronze/Silver/Gold/Platinum/VIP) or product cart, initiates payment via MTN MoMo or Orange Money through MeSomb.
2. An `orders` row is created with `status = 'pending'` before the payment request is sent — never after, so a webhook can never arrive before its order exists.
3. MeSomb sends a webhook to our endpoint on completion or failure.
4. **Webhook handler must**:
   - Verify the HMAC signature on every request; reject anything that doesn't verify, log the rejection, and never process an unverified payload
   - Check `mesomb_webhook_events` / `processed_payments` for the event's idempotency key before doing anything — if already processed, return success immediately without reprocessing (MeSomb and most payment providers retry webhooks; duplicate processing must be impossible)
   - Log the raw payload to `mesomb_webhook_events` regardless of outcome, for audit/replay
   - **If the event indicates success**: update the matching `orders` row to `status = 'completed'`, set `paid_at`, set `transaction_id`/`mesomb_transaction_id`; if this was a distributor pack purchase, activate (or create) the `distributors` row — set `status = 'active'`, `pack_tier`, `pack_price_xaf`, `pack_pv`, generate a unique `distributor_code` and `referral_link` if not already set, and place them into the sponsor's binary tree (see System 3 below) using `placement_id`/`placement_leg`; credit any applicable Sponsoring/Levelling bonuses to the upline's `wallets` via `wallet_transactions` and log them in `commissions`
   - **If the event indicates failure or cancellation**: update the `orders` row to `status = 'cancelled'` (or `failed` — pick one convention and use it consistently), do not create/activate any distributor record, and do not credit any commissions. Never leave an order in `pending` indefinitely — a webhook that unambiguously reports failure must resolve the order, not just log and stop.
   - Notify the customer (WhatsApp, using the existing `whatsapp_notified` pattern already on `orders`) on both success and failure — a silent failure is a support-ticket generator.
5. Add a safety-net job (cron or scheduled function) that finds `orders` stuck in `pending` beyond a reasonable timeout (e.g. 30 minutes) and either re-queries MeSomb's transaction status endpoint directly to resolve them, or marks them `expired` — never let an order sit in limbo indefinitely on webhook delivery failure alone.

**Non-negotiables:**
- Every state transition (`pending` → `completed`/`cancelled`) happens exactly once per order — verify this with a unique constraint or transactional check, not just application-level "hope."
- No commission or PV is ever credited except as a direct result of a verified, completed payment event.
- All amounts are handled as integers (XAF has no subunits) — never floats.

## 6. System 4 — Distributor Dashboard with 12-generation binary tree

Build an authenticated distributor-only dashboard (`/dashboard` or similar, gated by `profiles.role = 'distributor'` or equivalent) with:

### 6.1 Profile & referral
- Display distributor's profile details (name, phone, email from `profiles`), `distributor_code`, current `rank` / `rank_tier_id` (joined to `rank_tiers` for the label), `pack_tier`, `status`, `joined_at`
- Prominent, copyable `referral_link` (format: `https://songtai-life.vercel.app/join?ref={distributor_code}` or the existing join-flow convention already in the repo — check before inventing a new one) with a native share button (WhatsApp share intent especially, given this market)

### 6.2 Binary tree visualization — down to 12 generations
- Render the distributor's downline as a binary tree (left leg / right leg), starting from the distributor at the root
- Support drilling down through all 12 generations that the compensation plan's Leadership Bonus can pay on (per `rank_tiers.generation_pcts`) — this does not mean rendering all 12 levels flat and expanded by default (that would be visually unusable at scale); use a collapsible/expandable tree UI, defaulting to 2–3 generations expanded with a way to drill deeper
- Each node shows: name/distributor code, rank, personal PV, and which leg they occupy
- Show aggregate figures at the top: total downline count, `left_leg_pv`/`right_leg_pv` (current unpaid volume), weaker-leg volume (this is what the weekly Performance Bonus actually pays on — surface it clearly since it's the number distributors care about most)

### 6.3 PV, commissions & earnings summary
- Weekly Performance Bonus estimate: `weaker_leg_pv × rank_tiers.weekly_bonus_pct`, capped at `weekly_ceiling_xaf` for their rank — show both the calculated bonus and confirmation of whether it's capped
- Leadership Bonus breakdown per generation (1st through 12th, using `rank_tiers.generation_pcts` — zero-value generations for lower ranks should show as locked/greyed out with an explanation like "Reach Platinum to unlock Generation 4", not just silently absent)
- Commission history table (from `commissions`), wallet balance and transaction history (from `wallets`/`wallet_transactions`), and withdrawal history/request flow (from `withdrawals`) with clear pending/approved/paid status
- All monetary figures in XAF, formatted with thousands separators, never as raw integers

### 6.4 Non-negotiables
- All PV/commission calculations must be computed server-side (database function or server action) from source tables — never trust a client-computed number for anything that affects payouts
- The tree query for 12 generations must be efficient (recursive CTE or materialized closure table) — don't recursively fetch one level per round-trip from the client
- Every figure shown must be traceable back to the `commissions`/`wallet_transactions` tables — no "display-only" numbers invented in the frontend
