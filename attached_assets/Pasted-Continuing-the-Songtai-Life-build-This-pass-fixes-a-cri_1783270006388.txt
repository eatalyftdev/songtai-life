1. ROOT-CAUSE THE "DELETES DON'T REFLECT ON FRONTEND" BUG — DIAGNOSE BEFORE FIXING
═══════════════════════════
This symptom (admin panel deletes/updates work, but the public site keeps showing stale data) has a small number of likely causes — check all of them, don't just apply one fix blindly:

**a) Public pages are using ISR/SSG without on-demand revalidation.** If Products/Testimonials/Gallery/Events pages use `revalidate: 60` (or similar) instead of fetching fresh on every request or subscribing to Realtime, a delete in the admin panel won't show up until the next ISR window — which can look like "it's just broken" rather than "it's slow." Fix: either (i) reduce revalidate windows for content that changes often, or (ii) — the correct fix — trigger **on-demand revalidation** from every admin write:
```ts
// After any admin insert/update/delete in useAdminResource, call:
await fetch('/api/revalidate', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ path: '/products' }), // or /gallery, /events, /, etc.
});
```
```ts
// app/api/revalidate/route.ts
import { revalidatePath } from 'next/cache';
export async function POST(req: Request) {
  const { path } = await req.json();
  revalidatePath(path);
  return Response.json({ revalidated: true, path });
}
```
Map every admin resource to the specific public path(s) it affects (a product delete should revalidate `/products`, `/products/[slug]`, AND `/` since Featured Products lives on the homepage) — build this mapping explicitly rather than guessing per-case.

**b) The homepage specifically caches independently of the resource's own list page.** Even if `/products` revalidates correctly, the homepage's Featured Products / Testimonials / Gallery Teaser / Upcoming Events sections may be fetched with their own separate cache that isn't included in the revalidation call above. Explicitly include `/` (and `/en`, `/fr` if locale-prefixed routing means these are distinct cache entries) in the revalidation path list for every resource type shown on the homepage.

**c) Deleted records aren't actually being deleted — check for soft-delete vs hard-delete mismatches.** If a table has a `deleted_at` or `is_active`/`is_published` column, confirm the admin "delete" action actually sets this (or hard-deletes the row) AND that every public-facing query filters on it correctly (`.eq('is_active', true)` / `.is('deleted_at', null)`). A common bug: admin UI shows the item as gone because ITS OWN query filters on a flag, while the public query doesn't filter on that same flag and still returns the row.

**d) Client-side data fetched once on mount with no Realtime subscription and no revalidation.** For any component that fetches with a one-time `useEffect` + `supabase.from(...).select()` and never re-fetches, add a Supabase Realtime subscription (same pattern already used in the admin panel) so deletes propagate live to any client with the page open, in addition to the ISR fix in (a)/(b) which handles fresh server-rendered visits.

**e) Browser or CDN caching on the response itself.** Check response headers on the affected public pages for aggressive `cache-control` (e.g., `s-maxage` set very high with no matching revalidation tag) — Vercel's Edge Cache can hold a stale response independently of Next.js's own ISR cache if these aren't configured consistently.

Fix all applicable causes above, then explicitly test: delete a product/testimonial/gallery image/event in the admin panel, and confirm it disappears from the relevant public page(s) and the homepage within a few seconds without a hard refresh, in an incognito session (to rule out any client-side cache masking the real behavior).

4. THEME CONTRAST FIX — TEXT MUST BE LEGIBLE IN BOTH MODES, INCLUDING COLORED TEXT
═══════════════════════════
Audit every text color token currently in use. The core rule: **text color is never hardcoded to a fixed value that ignores the active theme** — every text color must be a CSS variable that flips appropriately between light and dark mode, including colored (non-neutral) text.

```css
:root {
  /* Light mode (default) */
  --text-primary: #0B0F0C;      /* near-black, not pure black — matches existing dark-bg token reused as light-mode text */
  --text-secondary: #4B5563;
  --text-on-green: #FFFFFF;      /* text sitting on a green-fill button/badge stays white in both modes */
  --text-accent-gold: #92751C;   /* darker gold variant for AA contrast on white — pure #C9A227 fails contrast as text-on-white */
  --text-accent-green: #0A7D32;
}

[data-theme='dark'] {
  --text-primary: #F5F5F0;       /* light, warm off-white — not pure white, matches the near-black bg's softness */
  --text-secondary: #A3A8A0;
  --text-on-green: #FFFFFF;
  --text-accent-gold: #E0C158;   /* lighter gold variant for AA contrast on the near-black dark background */
  --text-accent-green: #4ADE80;  /* lighter green variant — the deep #0A7D32 fails contrast as text on a dark bg */
}
```
Apply this systematically:
- Any place gold (`#C9A227`) or green (`#0A7D32`) is currently used as a **text color** (not a background fill) — headings, links, badges-as-text, accent labels — must switch to the theme-appropriate lighter/darker variant above, not the raw brand hex, since the raw brand hex frequently fails WCAG AA contrast against one of the two background modes.
- Run an actual contrast check (axe-core, already part of the CI pipeline from the testing strategy established earlier, or a manual contrast checker) on every text/background combination across both themes — gold-on-white and green-on-dark are the two combinations most likely to still fail even after this fix, per the accessibility risk flagged as far back as the original spec.
- Confirm every component (admin panel included, not just the public site) pulls from these same variables — no component-local hardcoded text colors that bypass the theme system.

6. EVERY HOMEPAGE SECTION EDITABLE FROM THE ADMIN PANEL

Beyond Products/Testimonials/Gallery/Events (already data-driven), the homepage almost certainly still has hardcoded copy for: the Hero headline/subheadline/CTA button text, the Company Introduction story text and stat labels/numbers, the Opportunity section's timeline step labels, the Distributor Benefits section's headline/icons/text, and the Newsletter section's headline/copy. Make all of this admin-editable:

```sql
create table homepage_sections (
  id uuid primary key default uuid_generate_v4(),
  section_key text unique not null,  -- 'hero', 'company_intro', 'opportunity', 'benefits', 'newsletter'
  content jsonb not null,             -- flexible per-section shape, bilingual fields nested inside
  updated_at timestamptz default now(),
  updated_by uuid references profiles(id)
);

alter table homepage_sections enable row level security;
create policy "public_read_homepage_sections" on homepage_sections for select using (true);
create policy "admin_homepage_sections_all" on homepage_sections for all using (is_admin()) with check (is_admin());
```
